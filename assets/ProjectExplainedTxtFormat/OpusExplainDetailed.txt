## Part 1: Refined Project Vision & Competitive Differentiation

### What Makes OpusHunter Genuinely Unique

Most job application tools are glorified job boards with a cover letter template. OpusHunter is an **autonomous career intelligence engine**. The differentiation stack:

**1. Tri-Strategy Cover Letter Intelligence**
Rather than one prompt style, OpusHunter runs three parallel generation strategies and selects the optimal output via a configurable fallback chain:

- **Strategy A — Mirror Matching:** Gemini analyzes the job description's exact language patterns, keyword density, and tone fingerprint, then mirrors that linguistic style in the cover letter. If the JD uses "drive impact at scale," the letter uses that exact register. ATS systems score higher when language mirrors the posting.
- **Strategy B — Achievement Amplification:** Extracts the top 3 quantified achievements from the user's career context that are most semantically similar to the job requirements (using Gemini's embedding capabilities), then builds the letter around those specific proof points with before/after impact framing.
- **Strategy C — Insider Narrative:** Gemini performs a simulated company research synthesis using the job description's implicit signals (company stage, team culture language, growth indicators) to craft a letter that demonstrates insider knowledge of the company's actual challenges — not generic "I admire your mission" filler.

The fallback chain is configurable per user: default is A → B → C, but users can reorder or disable strategies. The system scores each generated output on a rubric (ATS keyword density, specificity score, filler phrase count) and presents the highest-scoring version, with the others available as alternatives.

**2. Career Intelligence Graph**
The `user_context` table is not a flat document dump — it's a structured career knowledge graph. Every document upload enriches a persistent semantic model of the user's career. Over time, the system learns which skills cluster together in the user's background, which achievements resonate most with which job types, and which tone produces the best application outcomes. This graph is the foundation for increasingly personalized outputs over time.

**3. Application Outcome Learning Loop**
When a user marks an application as `interview` or `offer`, the system logs which cover letter strategy, which skill emphasis, and which tone was used. Over time, this creates a personal feedback signal that biases future generation toward what actually works for this specific user in this specific market.

**4. Parallel Multi-Source Intelligence with Cross-Source Deduplication**
Most tools hit one API. OpusHunter fires JSearch and Adzuna simultaneously, deduplicates using deterministic hashing, and keeps the richer record when the same job appears on both sources. The scraper registry pattern means adding LinkedIn, Indeed, or any future source is a single adapter file — zero orchestration changes.

**5. Autonomous Dispatch with Hard Links**
The application doesn't just generate a cover letter — it packages the cover letter with direct apply links and, where the apply URL is a direct email, can pre-compose the application email. This is the "one tap to apply" promise.

### RLS Policies (All Tables)

**Standard user-scoped policy pattern (applied to: profiles, user_documents, user_context, job_listings, job_applications, cover_letters, scrape_rate_limits, cover_letter_outcomes):**
```
SELECT: auth.uid() = user_id
INSERT: auth.uid() = user_id
UPDATE: auth.uid() = user_id
DELETE: auth.uid() = user_id
```

**Locked-down tables (user_api_keys, system_api_keys):**
```
ALL OPERATIONS: false (no client access — Service-Role only)
```

**Read-only for users (api_key_usage_logs):**
```
SELECT: auth.uid() = user_id
INSERT: false (Service-Role only)
UPDATE: false
DELETE: false
```

## Part 4: Edge Function Architecture (Detailed)

### `_shared/keyResolver.ts` — Triple-Tier Key Cascade

**Input:** `{ userId: string, provider: ApiProvider, serviceClient: SupabaseClient }`

**Resolution Logic:**
```
Tier 1: Query user_api_keys WHERE user_id = userId AND provider = provider AND is_active = true
  → If found: decrypt key, return { key, source: 'user' }

Tier 2: Query system_api_keys WHERE provider = provider AND is_active = true
         AND (throttled_until IS NULL OR throttled_until < now())
         ORDER BY priority_order ASC
  → For each key in order:
      → Try the API call
      → On 429: UPDATE system_api_keys SET throttled_until = now() + interval '1 hour'
                 Continue to next key
      → On success: UPDATE system_api_keys SET last_used_at = now()
                    Return { key, source: 'system', keyId }

Tier 3: All keys exhausted or throttled
  → Return { error: 'quota_exhausted', retryAfter: earliest throttled_until timestamp }

After every resolution attempt:
  → INSERT into api_key_usage_logs with all metadata
```

### `scrape-jobs/index.ts` — Multi-Source Parallel Scraper

**Request payload:**
```typescript
{
  userId: string,
  searchParams: {
    keywords: string[],
    workTypes: WorkType[],
    countries: string[],
    cities: string[],
    radiusKm: number,
    experienceLevel: SeniorityLevel,
    datePosted: '24h' | '7d' | '30d',
    page: number
  }
}
```

**Execution flow:**
```
1. Verify JWT → extract userId
2. Check scrape_rate_limits:
   - If member role AND last_scrape_at within 24h → return rate_limited error
   - If premium with own API key → bypass limit
3. Resolve API keys for rapidapi and adzuna via keyResolver
4. Build adapter configs for each registered scraper
5. Fire Promise.allSettled([jsearchAdapter.fetch(params), adzunaAdapter.fetch(params)])
6. Collect fulfilled results, log rejected with error details
7. Normalize all results to unified JobListing schema
8. Compute dedup_hash = sha256(normalize(company.toLowerCase() + title.toLowerCase() + location.toLowerCase()))
9. Filter out hashes already in job_listings for this user
10. For cross-source duplicates (same hash from both sources): merge, keeping richer record
11. Upsert up to 30 listings into job_listings
12. Update scrape_rate_limits for this user
13. Return { listings, total, page, sources: { jsearch: n, adzuna: n }, nextAvailableAt }
```

**Scraper Adapter Interface:**
```typescript
interface ScraperAdapter {
  name: JobSource
  fetch(params: SearchParams, apiKey: string): Promise<RawJobListing[]>
  normalize(raw: RawJobListing): JobListing
  getRegionalEndpoint(country: string): string
}
```

**Sweden-specific handling:**
- JSearch: `location=Stockholm, Sweden`, `country=SE`, `language=en`
- Adzuna: endpoint `https://api.adzuna.com/v1/api/jobs/se/search/1`
- Swedish cities mapped to lat/lng for haversine radius filtering:
  ```
  Stockholm:    59.3293, 18.0686
  Göteborg:     57.7089, 11.9746
  Malmö:        55.6050, 13.0038
  Uppsala:      59.8586, 17.6389
  Västerås:     59.6099, 16.5448
  Örebro:       59.2741, 15.2066
  Linköping:    58.4108, 15.6214
  Helsingborg:  56.0465, 12.6945
  Jönköping:    57.7826, 14.1618
  Norrköping:   58.5877, 16.1924
  ```
- Post-fetch haversine filter: if `radiusKm` is set and listing has lat/lng, filter out listings beyond radius

### `extract-context/index.ts` — Career Intelligence Extraction

**Execution flow:**
```
1. Receive { userId, documentId, storagePath }
2. Download binary from Supabase Storage via Service-Role client
3. Detect MIME type:
   - application/pdf → extract text via Deno PDF parser
   - application/vnd.openxmlformats-officedocument.wordprocessingml.document → parse DOCX XML
   - text/plain → use directly
4. Resolve Gemini API key via keyResolver
5. Send extraction prompt to Gemini requesting structured JSON output:
   {
     extracted_skills: string[],
     extracted_experience: ExperienceEntry[],
     extracted_education: EducationEntry[],
     extracted_certifications: CertEntry[],
     career_summary: string,
     key_achievements: string[],
     skill_clusters: { [cluster: string]: string[] },
     tone_preference: string
   }
6. Validate JSON response structure
7. Upsert into user_context (merge with existing if present — don't overwrite, enrich)
8. Update user_documents.extraction_status = 'complete'
9. Log token usage to api_key_usage_logs
10. Return { success: true, contextId, skillCount, achievementCount }
```

**Skill cluster extraction (unique feature):**
The prompt instructs Gemini to group skills into semantic clusters:
```json
{
  "skill_clusters": {
    "backend_engineering": ["Node.js", "PostgreSQL", "Redis"],
    "cloud_infrastructure": ["AWS", "Terraform", "Docker"],
    "leadership": ["Team management", "Hiring", "OKR planning"]
  }
}
```
These clusters are stored in `user_context.skill_clusters` and used by the cover letter generator to select the most relevant skill cluster for each job type.

### `generate-cover-letter/index.ts` — Tri-Strategy Generation Engine

**Execution flow:**
```
1. Receive { userId, jobListingId, strategy?: CoverLetterStrategy }
2. Fetch in parallel:
   - user_context for userId
   - profiles for userId
   - job_listings record for jobListingId
3. If no strategy specified: run all three strategies in parallel
4. For each strategy:

   STRATEGY A — Mirror Matching:
   → Analyze JD language: extract tone, register, key phrases, verb patterns
   → Prompt: "Mirror the linguistic style of this job description exactly.
              Use the same register, similar sentence structure, and echo
              key phrases naturally. Do not copy — mirror."
   → Include: user's top 5 skills matching JD keywords

   STRATEGY B — Achievement Amplification:
   → Score each key_achievement for semantic similarity to JD requirements
   → Select top 3 highest-scoring achievements
   → Prompt: "Build this letter around these three specific achievements
              with before/after impact framing. Every paragraph must
              reference measurable outcomes."
   → Include: quantified metrics, percentages, team sizes, revenue impact

   STRATEGY C — Insider Narrative:
   → Analyze JD for implicit signals: company stage, team culture, growth phase
   → Prompt: "Write as if you deeply understand this company's specific
              challenges. Reference the implicit problems this role solves.
              Demonstrate you've thought about their situation, not just
              your qualifications."
   → Include: company name used 2–3 times naturally, role-specific insight

5. Score each output:
   → ATS score: keyword match density vs JD
   → Specificity score: ratio of specific claims to generic statements
   → Filler phrase count: detect and penalize generic phrases

6. Select highest-scoring strategy as primary
7. Store all three versions in cover_letters.alternative_versions (jsonb array)
8. Store primary in cover_letters.content
9. Log generation metrics
10. Return complete cover_letters record with all versions
```

**Cover letter quality rules (enforced in prompt):**
```
MANDATORY:
- 4–5 paragraphs exactly
- Opening: specific hook referencing exact role title and company name
- No "I am writing to express my interest" or equivalent
- No "I believe I would be a great fit"
- No "passionate about" without specific evidence
- Every achievement must have a number or measurable outcome
- Closing: specific call to action, not "I look forward to hearing from you"
- Total length: 280–380 words

STRUCTURE:
P1: Hook — specific role + company + one compelling credential
P2: Top 3 skill/achievement matches to JD requirements (quantified)
P3: Company-specific insight + why this role specifically
P4: Technical depth + certifications relevant to this role
P5: Confident close with specific next step
```

### `score-cover-letter/index.ts` — ATS Intelligence Scorer

**This is a unique Edge Function that no competitor has:**
```
1. Receive { coverLetterId, jobListingId }
2. Fetch cover letter content and job description
3. Run scoring algorithm:

   ATS Score (0–100):
   → Extract keywords from JD (nouns, technical terms, role-specific phrases)
   → Count keyword appearances in cover letter
   → Score = (matched_keywords / total_jd_keywords) * 100
   → Bonus: exact phrase matches score 2x

   Specificity Score (0–100):
   → Count sentences with numbers/percentages/proper nouns
   → Count sentences with only generic claims
   → Score = (specific_sentences / total_sentences) * 100

   Filler Phrase Detection:
   → Check against filler phrase dictionary (50+ phrases)
   → Count occurrences
   → Each occurrence -5 points from total

4. Update cover_letters with scores
5. Return { atsScore, specificityScore, fillerCount, suggestions: string[] }
```

### `geo-autocomplete/index.ts` — GeoDB Proxy

```
1. Receive { query: string, countryCode?: string }
2. If query length < 2: return []
3. Build GeoDB request with:
   - namePrefix = query
   - countryIds = countryCode if provided
   - minPopulation = 10000 (filter tiny villages)
   - limit = 10
4. If countryCode = 'SE' or query matches Swedish patterns:
   → Prepend Swedish cities from hardcoded priority list if they match query
5. Return normalized city array
```

### `save-api-key/index.ts` — Secure Key Storage

```
1. Verify JWT
2. Receive { provider, key } — key is plaintext from client
3. Validate key format for provider (basic format check)
4. Encrypt key using Supabase Vault or AES-256 with server-side secret
5. Upsert into user_api_keys via Service-Role client
6. Return { success: true } — never return the key
```

## Part 9: Security Architecture

### Zero-Trust Security Model

```
Client-side (never trusted):
  → All sensitive operations go through Edge Functions
  → API keys never touch client code
  → User role never trusted from client — always verified server-side
  → JWT verified on every Edge Function call

RLS enforcement:
  → Every table has RLS enabled
  → Default deny: no policy = no access
  → user_api_keys: RLS blocks all client access (Service-Role only)
  → system_api_keys: RLS blocks all client access (Service-Role only)
  → Admin data: only accessible via SECURITY DEFINER functions

Edge Function security:
  → Verify JWT on every request: const { data: { user } } = await supabase.auth.getUser(jwt)
  → Never trust userId from request body — always extract from verified JWT
  → Service-Role client only used inside Edge Functions, never returned to client
  → CORS: restrict to app domains only

Key encryption:
  → API keys encrypted before storage using Supabase Vault
  → Keys never logged, never returned after initial save
  → Only last 4 characters shown in UI after saving

Admin verification:
  → Admin routes: check profiles.role = 'admin' via SECURITY DEFINER function
  → Double-checked: client-side (hide UI) + server-side (block data)
  → Admin Edge Functions verify role before any data access
```

## Part 14: Key Engineering Decisions & Rationale

### Why Tri-Strategy Cover Letters?

Single-strategy AI cover letters are a commodity. Every tool does it. The tri-strategy approach with scoring creates a defensible moat:
1. Users get objectively better letters (highest-scoring version)
2. The scoring system is transparent and educational
3. Users can see why one version scored higher
4. The outcome learning loop means the system improves per-user over time
5. No competitor has this — it's a genuine product differentiator

### Why the Scraper Registry Pattern?

The `const scrapers: ScraperAdapter[] = [jsearchAdapter, adzunaAdapter]` pattern means:
- Adding LinkedIn scraper = create `linkedin.ts` + add to array
- Zero changes to orchestration, deduplication, or storage logic
- Each adapter is independently testable
- Failed adapters don't block others (Promise.allSettled)

### Why Deterministic Dedup Hashing?

`sha256(normalize(company + title + location))` ensures:
- Same job from JSearch and Adzuna = one record (richer one kept)
- Re-scraping doesn't create duplicates
- Hash is deterministic across scrape runs
- Normalization (lowercase, trim, remove punctuation) handles minor variations

### Why SECURITY DEFINER for Admin Functions?

Admin users should not have direct table access — they should only access data through controlled functions that:
1. Verify the caller is actually an admin (double-check)
2. Return only the data needed (no SELECT *)
3. Log the access
4. Can be audited and modified without changing RLS policies

### Why Outcome Learning Loop?

The `cover_letter_outcomes` table creates a feedback signal that no static tool can replicate. When a user gets an interview after using Strategy B with Achievement Amplification, that signal biases future generation for similar job types toward Strategy B. Over time, the system learns what works for each user in each market — this is the long-term moat.
